# docx-mcp 工具过滤代理 · 使用文档

> 脚本位置：`mcp_filters/docx_tool_filter.py`
> 建立时间：2026-09-28
> 适用客户端：CodeBuddy（及其他任意 MCP 客户端）
> 作用：把 `docx-mcp-server` 的 **219 个工具收敛为 47 个**，降低上下文开销

---

## 一、它解决什么问题

`docx-mcp-server` 是一个功能极全的 Word 文档处理服务器，注册了 **219 个工具**。这些工具定义会在**每一轮请求**里全部塞进模型上下文，粗略估算占 **2~3 万 token**。

问题在于，其中约 80% 的工具对「中文课题文档的阅读与编辑」这个场景毫无用处（内容控件、图表、公式、邮件合并、诉讼取证、PII 脱敏、底层 XML 操作……）。它们不仅浪费上下文，还会稀释模型对真正相关工具的注意力。

**目标**：只保留实际会用的工具，其余隐藏。

---

## 二、为什么不能在服务端直接关（结论：做不到）

尝试过三条路，只有第三条可行：

| 路径 | 结果 | 依据 |
|---|---|---|
| ① 服务端环境变量 | ❌ 不支持 | `docx_mcp/server.py` **根本没有 `import os`**，不存在任何 `os.environ` / `os.getenv` 读取 |
| ② 服务端 CLI 参数 | ❌ 不支持 | `main()` 全文只有 `mcp.run()` 一行，无参数解析 |
| ③ 客户端 `disabledTools` 字段 | ❌ 实测无效 | 在 `.mcp.json` 里写入该字段并重载后，被禁工具**依旧出现**在工具列表中，说明客户端忽略了未知字段 |
| ④ **夹一层过滤代理** | ✅ **可行** | 本方案 |

补充：服务端所有工具都是 `@mcp.tool()` **裸装饰器无条件注册**，导入即生效；既没有条件判断，也没有覆盖 `tools/list` 的过滤逻辑。

## 三、方案架构

```
                       .mcp.json
                           │
              ┌────────────┴────────────┐
              │                         │
   改前：CodeBuddy ──stdio──> docx-mcp-server          （219 个工具全进上下文）
   改后：CodeBuddy ──stdio──> 过滤代理 ──stdio──> docx-mcp-server
                                ↑
                        只放行白名单里的 47 个
```

代理做两件事：

1. **列表层过滤**：启动时拉取上游全量工具，只把白名单内的返回给客户端；
2. **调用层拦截**：即使客户端拿到了被禁工具的名字，调用也会被拒绝（双重保险）。

## 四、当前配置

`.mcp.json`（工作区根目录）中的对应条目：

```json
"docx-mcp-server": {
  "type": "stdio",
  "command": "/home/demo/.local/bin/uv",
  "args": [
    "run",
    "--script",
    "/home/demo/桌面/人工智能项目/mcp_filters/docx_tool_filter.py"
  ],
  "env": {
    "PATH": "/home/demo/.local/bin:/usr/local/bin:/usr/bin:/bin"
  },
  "disabled": false,
  "timeout": 180000
}
```

要点：

- 用 **`uv`** 而不是 `uvx` —— 脚本走 PEP 723 内联依赖声明（`dependencies = ["mcp<2", "anyio"]`），由 `uv run --script` 自动准备环境，**无需任何额外安装**。
- `env.PATH` 里的 `/home/demo/.local/bin` 是留给**代理进程**的：代理内部要用 `uvx` 拉起上游 `docx-mcp-server`，而 GUI 客户端的 PATH 是启动时的快照，未必包含该目录。
- 依赖里必须含 **`mcp<2`**。上游 `docx-mcp-server` 用的是 `from mcp.server.fastmcp import FastMCP`，而 mcp 2.x 已把 `FastMCP` 改名为 `MCPServer`，不钉版本会直接崩溃。
- `timeout` 保持 180000（180 秒）：多了一层进程，冷启动约 3~6 秒。

## 七、日常操作

所有调整都是**改 `docx_tool_filter.py` 里的 `ALLOW` 元组**，改完在客户端重载 MCP 即可生效。

### 7.1 加回某个工具

比如发现要改页眉页脚，编辑脚本，往 `ALLOW` 里补上：

```python
    # --- 页眉页脚（按需开启） ---
    "get_headers_footers",
    "edit_header_footer",
```

工具名从上游公告里挑。**写错名字不会静默失败** —— 代理会在 stderr 打印警告：

```
[docx-filter] 警告: 白名单中的这些工具在上游不存在 -> ['set_paragraph_format']
```

（这条警告是真实踩到的：白名单里曾误写 `set_paragraph_format`，上游并无此工具，已删除。）

### 7.2 再砍一些工具

从 `ALLOW` 里删行即可。或者在 `.mcp.json` 里加环境变量做**不改代码的临时削减**：

```json
"env": { "DOCX_MCP_DENY": "get_reading_time,get_statistics" }
```

### 7.3 临时关闭过滤（排查用）

```json
"env": { "DOCX_MCP_ALLOW": "all" }
```

此时全部 219 个工具透传，退化为直连。排查「是不是代理导致的」时很有用。

### 7.4 查看放行明细

```json
"env": { "DOCX_MCP_VERBOSE": "1" }
```

stderr 会打印完整放行清单。

### 7.5 手动运行（不经过客户端）

```bash
/home/demo/.local/bin/uv run --script "/home/demo/桌面/人工智能项目/mcp_filters/docx_tool_filter.py"
```

正常表现：stderr 出现 `上游 219 个工具 -> 放行 47 个，隐藏 172 个`，然后等待 stdin 上的 JSON-RPC。

## 八、环境变量速查

| 变量 | 作用 | 示例 |
|---|---|---|
| `DOCX_MCP_ALLOW` | 覆盖白名单（逗号分隔）；`all` = 关闭过滤 | `"open_document,get_body_text"` |
| `DOCX_MCP_DENY` | 在白名单基础上再禁用（逗号分隔） | `"get_reading_time"` |
| `DOCX_MCP_VERBOSE` | `1` = 打印放行明细到 stderr | `"1"` |

优先级：`DOCX_MCP_ALLOW` > 脚本内 `ALLOW`，最后统一减去 `DOCX_MCP_DENY`。

## 九、故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 重载后工具仍是 219 个 | 客户端缓存了工具列表 | **完全退出客户端再启动**，不只是 Reload |
| 服务器显示「连接失败」 | 代理或上游启动异常 | 手动运行 7.5 的命令看 traceback |
| 冷启动超时 | 首次跑 `uv run --script` 要准备依赖 | 手动跑一次预热；确认 `timeout` 为 180000 |
| 报 `No module named 'mcp.server.fastmcp'` | mcp 升到了 2.x | 确认脚本内依赖为 `mcp<2`（上游兼容性要求） |
| 某个工具调用提示「已被过滤代理禁用」 | 该工具不在白名单 | 加进 `ALLOW`（见 7.1） |
| stderr 提示白名单工具在上游不存在 | 工具名拼写错误或上游改名 | 按警告修正名称 |

## 十、复用到其他 MCP 服务器

这个代理**不限于 docx**。要在别的「工具爆炸」的 MCP 服务器上复用，只改脚本顶部三处：

```python
# ① 上游启动命令
UPSTREAM_COMMAND = "uvx"
UPSTREAM_ARGS = ["--with", "mcp<2", "docx-mcp-server"]

# ② 白名单（留空则全部透传，等同不过滤）
ALLOW: tuple[str, ...] = ( ... )
```

然后把 `.mcp.json` 里该服务器的 `command`/`args` 指向同一份脚本，并在 `env` 里用 `DOCX_MCP_ALLOW` 指定不同的白名单即可。同一份脚本可以被多个服务器共用。

## 十一、实现要点（供二次修改参考）

| 关注点 | 做法 |
|---|---|
| 上游生命周期 | `stdio_client` + `ClientSession` 上下文管理器，代理启动时先 `initialize()` 上游 |
| 工具分页 | `_collect_tools()` 循环处理 `nextCursor`，防止上游工具多于一页时漏掉 |
| stdout 纪律 | **所有日志走 stderr**，stdout 只留给 JSON-RPC，否则会污染协议流 |
| 调用转发 | 优先返回 `result.content`；为空时回退到 `structuredContent` |
| 结构化输出 | **必须去掉暴露工具的 `outputSchema`**。代理只重放 `content`，若保留该字段，SDK 会以「声明了结构化输出却未返回」为由拒绝调用 |
| 异常兜底 | 上游调用异常被捕获后转成一条文本结果返回，**不让代理进程崩掉** |
| 服务标识 | `Server("docx-mcp-filtered")`，便于在日志里区分代理与上游 |
